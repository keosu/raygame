# RayGame 产品化评审与实施路线

评审日期：2026-10-09。代码基线：`69565f1`，版本：0.2.0。

以下评审保留该基线时的观察；当前实施进度见第 10 节起的实施跟踪。

本评审覆盖公开头文件、运行时实现、四个示例、xmake、CI 和现有测试。
推荐定位是面向小团队、以代码开发为主的桌面 2D 游戏框架，优先保证
Windows/MSVC 与 Linux，保留 raylib 后端和 GameObject/Component 使用方式。
这是实施建议，不代表下述模块已经实现，也不代表已作出平台或性能承诺。

**1. 总体判断与产品边界**

当前版本已经形成可工作的 2D 运行时：生命周期、延迟销毁、固定物理步、
场景切换、层级变换、资源缓存、基础 UI，以及四个能运行的示例均已具备。
已有回归检查也覆盖了不少回调期间修改集合的情况。它适合作为原型开发基础。

产品化的主要缺口集中在生命周期边界、失败恢复、内容制作流程、可诊断性、
性能预算和独立项目交付。仅增加渲染效果或更多示例，不能消除这些缺口。

建议以一个完整的可分发游戏作为 1.0 的验收载体：主菜单 → 设置 → 关卡加载 →
游戏 → 暂停 → 结算 → 存档 → 退出 → 再次启动恢复。开发者应能在独立仓库中
完成这条流程，玩家机器无需安装 xmake 或 Visual Studio。

保留组件式开发；高密度子弹、粒子可使用紧凑数组。全面 ECS 重写、自研图形
后端、通用大型编辑器、网络同步和脚本热替换暂不进入首批交付范围。
macOS、Web、移动端分别通过需求和验证后再纳入承诺的平台矩阵。

**2. 证据、现有验证与边界**

上一轮在此代码基线上完成了 MSVC Debug/Release 构建，两种模式各有
137 个逻辑断言通过、图形 smoke 零失败，并检查了四个游戏的静默启动及暗色标题栏。
这说明已覆盖的行为正常；尚不能据此推断压力、异常和长期运行都可靠。
现有 smoke 导出预览图，没有自动图像差异验收。

本轮在独立的临时 xmake 项目中运行了三个无窗口探针，未改动引擎实现：

| 探针 | 实际结果 | 产品化含义 |
| --- | --- | --- |
| 组件的 `OnDestroy` 调用所属场景的 `CreateGameObject`，随后 `Scene::Clear(); Scene::Update();` | 新建对象仍然存活 | 清场景需要进入明确的清理状态，定义此时是否拒绝生成对象 |
| `Tick(1.0f)`，分别累计 `Update` 和 `FixedUpdate` 的时间 | `1.000000s` 与 `0.133333s` | 8 步上限可防止追帧失控，但需要统一模拟时间策略并单独保留真实时间 |
| 先注册全局事件，再 `LoadScene`、`Tick` 和发出该事件 | 回调次数为 0 | 当前切场景清空全局订阅的规则无法承载应用级服务 |

探针位于本地忽略目录 `build/readiness-probes`，结果用于证明上述行为。
后两个行为与当前实现规则一致，属于需要明确和改进的架构契约。
下表其余项来自静态审查，未把可能发生的问题表述为已经复现的崩溃。
本轮没有进行性能压测、覆盖率统计或新的跨平台运行测试。

**3. 优先处理的核心缺口**

P0 表示后续架构依赖的基础或有数据/生命周期风险的缺口；P1 表示完成目标
类型游戏所需的能力；P2 表示基于测量或具体项目按需增加。

| 编号 / 优先级 | 当前证据 | 影响与建议 | 验收要点 |
| --- | --- | --- | --- |
| R01 / P0 | `ResourceManager` 返回缓存元素的裸指针；`UnloadTextureNamed`、字体卸载直接删除元素；`SpriteRenderer`、`Tilemap`、`UI` 持有这些指针 | 卸载后仍使用资源会访问失效引用。采用带类型和代次的资源句柄，定义引用、卸载和替换规则 | 活跃渲染引用遇到卸载/替换不会访问失效内存；失败显示占位资源并给出可定位的错误 |
| R02 / P0 | `GameEngine::Init` 在 `InitWindow` 后直接标记成功；`Run` 仅在正常退出时调用 `Shutdown`；`Display::Begin` 先释放旧画布再创建新画布 | 初始化与重建失败缺少回滚；用户回调抛异常可能绕过正常清理。明确错误策略，使用 RAII 守卫持有原生资源 | 初始化任一步失败可清理已成功部分；画布重建失败保留可用画布；退出过程幂等 |
| R03 / P0 | `Scene::Clear` 与 `FlushPending` 允许销毁回调继续生成对象，探针已确认 | 明确 `Loading/Running/Clearing/Unloaded` 状态；清理期间禁止向该场景生成，或移交其他明确的作用域 | 清理结束无残留/复活对象；销毁回调只执行一次；外部保留引用也能识别对象失效 |
| R04 / P0 | `PhysicsWorld`、`EventBus`、`TweenManager` 等全局静态状态；`ApplyPendingScene` 清空三者 | 应用级服务、关卡与 UI 叠层难以独立存续。逐步引入显式运行上下文和作用域 | 更换关卡不清除应用事件/音乐服务；销毁作用域自动取消其回调；测试之间没有状态泄漏 |
| R05 / P0 | `Tick` 将完整 dt 传给普通更新，物理累计只接收最多 8 步；`Input` 直接调用 raylib 的帧按键接口 | 需要游戏时间、真实时间、固定 tick 与输入消费规则；在多次固定更新中直接读取 Down 可能重复消费，在零次固定更新帧可能遗漏 | 在 30/60/144 FPS 和长帧注入下，动作的边沿语义一致；暂停时菜单可更新；丢弃的追帧时间可观测 |
| R06 / P0 | `SaveSystem::Save` 以 `ios::trunc` 打开正式文件；示例使用相对路径 | 写入中断会留下不完整存档；工作目录和安装目录写权限不稳定。增加用户数据目录、临时文件原子替换、备份和版本迁移 | 注入写入/替换失败后旧存档仍可加载；中文路径、只读安装目录、损坏文件有明确处理 |
| R07 / P0 | 游戏静默配置调用 `SetTraceLogLevel(LOG_NONE)`；框架没有独立诊断服务 | 保持无控制台体验，同时增加文件日志、等级/类别、启动环境与错误上下文，开发版提供日志面板 | 发布包启动/资源错误可从日志定位；日志有容量上限；调试符号可匹配版本 |
| R08 / P1 | `GameObject::active` 公开可写，只控制自身遍历；`Component::SetEnabled` 与对象激活分离；缺少移除组件接口 | 明确自身激活与层级有效激活、回调配对、父级销毁规则；提供延迟安全移除 | 重复启停、父子启停、回调内移除、跨场景挂接都有契约与针对性测试 |
| R09 / P1 | `PhysicsWorld::Step` 对碰撞体两两扫描，复制接触表；只有圆和 AABB、单次冲量/位置修正 | 大场景与高速物体能力有限。增加空间粗筛、查询、必要的扫掠检测，或引入可选成熟物理后端 | 固定场景记录候选对和耗时；高速穿薄墙有测试；复杂堆叠的支持范围明确 |
| R10 / P1 | `UI` 是标签/按钮等静态绘制函数，按钮共享按下状态；无布局/焦点/输入捕获；字体只加载默认字符集 | 无法直接支持完整设置菜单、手柄操作和中文 UI。增加控件 ID、布局、焦点、模态路由和文字布局 | 菜单可全程键盘/手柄操作；模态层不让点击穿透；中文显示、回退字体和换行可验证 |
| R11 / P1 | 四个示例均在 C++ 中建立内容；`Tilemap` 没有文件导入和碰撞构建流程 | 缺少可持续制作内容的工具链。增加组件字段描述、版本化场景/预制体、地图和图集导入 | 新增关卡/敌人配置不改引擎代码；资源依赖缺失在打包前被发现 |
| R12 / P1 | CI 只构建示例与运行逻辑测试，xmake 使用 `latest`；产物共用 `bin`；没有完整发行流程和根目录 LICENSE | 构建通过尚未验证分发和下游接入。增加独立消费项目、固定/锁定构建输入、发行包与平台验收 | 不同配置产物不混用；干净机器运行发行包；依赖许可与符号随版本可追溯 |

R01 指的是元素被擦除/资源被卸载后的生命周期问题；`unordered_map` 的普通
rehash 本身不会使元素指针失效。修复应围绕所有权，避免针对错误原因重写容器。

R02 的 RAII 应落在资源持有者和运行会话上，不能简单依赖基类析构函数调用
派生类虚回调。选择允许或禁止业务回调抛异常后，需要让所有调度器一致执行。

**4. 建议的模块划分与依赖**

| 层 / 模块 | 职责 | 依赖与边界 |
| --- | --- | --- |
| Foundation | 错误结果、日志、计时、句柄、随机流、路径基础 | 逐步减少对 raylib 图形头的依赖；保持容易进行无窗口测试 |
| Platform / Application | 窗口、DPI、焦点、显示器、主题、输入设备、用户目录、应用配置 | 继续适配 raylib；仅在需要的边界封装，不先建设多图形后端体系 |
| Assets | 资源标识、元数据、加载状态、缓存、依赖、生命周期 | 后台线程读文件/解码；图形资源上传和释放在拥有图形上下文的线程执行 |
| World / Scenes | 对象、组件、变换、生命周期、作用域、场景叠层 | 每个世界拥有自己的物理、场景事件、计时任务与补间，应用服务独立存在 |
| Simulation | 固定 tick、碰撞查询、物理、游戏逻辑系统 | 显式定义更新顺序；表现层读取已完成的模拟状态 |
| Rendering / UI / Audio | 渲染队列、相机、界面、文字、音频播放 | 分离世界绘制和 UI 绘制；暂停策略可按域配置 |
| Content / Tools | 序列化、预制体、地图导入、资源浏览、Inspector、性能面板 | 工具读取公开描述和句柄；发布版可裁掉开发工具 |
| Packaging / SDK | 模板、资源收集、平台打包、版本与迁移说明 | 从独立游戏项目验证，不依赖引擎仓库的目录布局 |

先引入一个运行上下文，逐个迁移全局服务；现有静态 API 可短期提供兼容入口。
业务代码逐步获取明确的上下文引用。先保证单窗口、单活动游戏世界与 UI 叠层的
正确性，再视编辑器预览需求扩展多个世界。无需一次完成全部目录和命名迁移。

推荐的帧流程是：平台事件 → 输入快照与路由 → 应用/未缩放时间更新 →
固定 tick（消费输入命令 → 物理前逻辑 → 物理积分/求解 → 碰撞事件）→
表现更新与相机 LateUpdate → 按插值状态绘制世界 → UI → 提交画面。
接口应明确哪些阶段可以直接修改结构、哪些必须使用命令队列。

**5. 需要补齐的游戏开发能力**

| 模块 | 第一批可交付功能 | 后续按需求扩展 |
| --- | --- | --- |
| 应用配置 | 窗口模式、尺寸、帧率/VSync、失焦策略、音量、键位保存；引擎快捷键可配置 | 多窗口、平台特定能力 |
| 场景与状态 | 菜单/游戏/暂停的状态栈，加载页，资源预加载，持久服务 | 叠加世界、分区加载 |
| 资源系统 | 类型句柄、加载错误、占位资源、资源清单、使用计数与内存统计 | 异步加载、开发期纹理/着色器/配置热重载、资源包 |
| 序列化与预制体 | 稳定类型 ID、字段描述、默认值、格式版本、对象引用恢复、配置实例化 | 预制体覆写、编辑器撤销重做 |
| 地图与动画 | 选择一种地图格式导入，如 LDtk 或 Tiled；图集与动画片段导入；可见区域裁剪 | 分块地图、动画状态机、动画事件 |
| 物理查询 | 射线、区域重叠、形状扫掠、明确层过滤；完善命中结果的法线/位置 | 平台角色控制器、旋转刚体/关节与成熟求解器适配 |
| UI 与文字 | 布局、锚点、滚动、按钮/滑块/选项框、焦点导航、输入捕获；UTF-8 字形收集与字体回退 | 按产品需求补 IME 输入、复杂文字塑形、双向文字和屏幕阅读器集成 |
| 输入系统 | 动作/轴、上下文、重绑定、设备热插拔、边沿缓冲、键位显示 | 震动、触摸、录制回放 |
| 音频 | 独立播放实例、同音效重叠播放、Music/SFX/UI 音量分组、淡入淡出和暂停规则 | 距离衰减、优先级、设备切换 |
| 游戏通用模块 | 可配置计时器、带所有者的补间、简单状态机、相机边界和震屏 | 项目需要时加入 A*、对话、任务系统 |
| 开发工具 | 层级/组件检查器、对象选中、碰撞可视化、逐帧执行、日志/资源/性能面板 | 在序列化稳定后建设场景编辑功能 |

序列化只处理显式声明的持久字段，不直接保存裸指针、`std::function` 或 GPU
句柄。实例化需要“分配对象 → 填充配置 → 恢复引用 → 激活”的明确阶段；目前
`AddComponent` 立即调用 `Awake/OnEnable`，应先解决此契约再做通用反序列化。

文字支持要分清 UTF-8 字符串、字形覆盖和排版。当前
`LoadFontEx(..., nullptr, 0)` 仅加载默认字符集，美化英文 UI 并不意味着中文
已经可用。需要合适字体、字符集/动态字形缓存、测量换行与回退策略。

保留现有即时绘制帮助函数，用它们承载简单 HUD；完整游戏菜单应使用明确的
控件状态和输入路由。开发用 Inspector 可以评估成熟工具 UI 库，并将其依赖
做成可选项。无需把游戏 UI 和调试 UI 强制统一为同一套实现。

当前粒子模块也有功能契约未闭合：`endColor` 未参与更新，alpha 从 255 淡出，
没有使用初始 alpha；旋转数据被更新，但圆形绘制看不出旋转。应先让公开参数
生效或收缩其承诺，再增加贴图、曲线、局部/世界空间和预设编辑功能。

**6. 性能策略与物理选型**

先建立可重复的场景和测量，再决定改动。已看到的潜在热点包括：

- `PhysicsWorld::Step` 的两两检测及接触表复制。1,000 个碰撞体有 499,500
  个候选组合，每秒 60 步约 3,000 万次组合访问；这是组合数，不是实测耗时。
- `Scene::Render` 每帧把所有启用组件加入排序，包含不绘制内容的组件。
- `GameObject::Start/Visit` 复制组件引用列表；`GetComponent` 线性动态类型查询。
- `Transform` 多次递归计算世界变换，`Tilemap` 每帧遍历整张地图。
- `ObjectPool` 为对象分别分配内存；适合保证地址稳定，但不等于连续存储。
- `Display` 使用整数级超采样，尚无最大纹理尺寸、显存预算、像素画最近邻等质量策略。

弹幕示例使用独立 `BulletField` 检测，不能用它的表现证明通用物理世界能够
承受同等数量的刚体。raylib 自身已有批处理，需测量批次和状态切换后再决定
是否自建批处理。透明绘制顺序应优先正确，不能随意按贴图排序。

建议先做渲染组件注册、可见性裁剪、变换缓存与空间粗筛；保留安全的延迟修改
行为，再用命令队列/稳定存储减少快照分配。不要为了优化破坏已有生命周期保障。

物理上保留适合街机玩法的简单碰撞/查询；需要旋转刚体、摩擦、关节、稳定
堆叠时，评估 Box2D 等成熟库的可选适配。选择时记录坐标单位、步进、所有权、
事件格式、依赖版本和许可证。两套世界之间的交互须有规则，不能让它们同时
无约束地写同一对象的 Transform。

性能预算应绑定硬件、分辨率、发行配置和场景分布。60 FPS 的总帧预算是
16.67 ms，但不能提前给本项目承诺某个对象数量。建议建立 1k/5k/10k 精灵、
稀疏与密集碰撞、粒子、地图、UI 文字的独立基准，记录 p50/p95/p99 耗时、
候选对、绘制批次、稳态分配数及内存峰值。先保存基线，再为目标硬件定门槛。

**7. 质量、开发体验与发行标准**

| 领域 | 应补内容 | 建议的验收场景 |
| --- | --- | --- |
| 生命周期 | 契约测试、错误路径测试、ASan/UBSan 等可用检查器 | 重复切关/重试至少 1,000 次，资源计数回落到稳定基线；回调中销毁/清理/取消安全 |
| 时间与输入 | 可注入输入快照与时钟，固定种子随机流 | 不同渲染帧率下动作次数一致；暂停、失焦、长帧和重新绑定不丢边沿事件 |
| 文件与资源 | 故障注入、版本迁移、字段合法性与大小限制 | 资源缺失、解码失败、损坏存档、磁盘写失败、中文路径和只读目录 |
| 图形与平台 | 有图形环境的自动 smoke、可控视觉比较、实际硬件验证表 | 100/125/150/200% DPI，双屏移动，全屏往返，最小化/恢复；资源重建失败 |
| CI | 构建/逻辑/集成分层，编译告警与静态分析，固定工具版本和依赖解析 | Windows/MSVC 与 Linux Debug/Release；平台检查结果随版本保留 |
| SDK 消费 | 独立模板项目、按需包含头、公开 API 文档和兼容测试 | 安装框架后在另一个仓库构建；不引用引擎 examples 或源码路径 |
| 打包 | 按平台/架构/配置隔离输出，资源清单、运行库策略、符号、版本元数据 | 干净 Windows 机器和 Linux 目标环境运行完整发行包 |
| 文档与治理 | 根目录 LICENSE、第三方 notices、变更日志、API 弃用/迁移规则 | 发行内容与标注许可一致；升级框架有明确迁移说明 |

上述次数和矩阵是建议验收条件，不是本轮已经完成的测试。无窗口逻辑测试可
在普通 CI 上运行；图形 smoke 需要合适的显示/虚拟显示环境，驱动相关行为
仍需要实际硬件验证。长稳测试至少覆盖一段持续游戏会话并观察内存趋势。

逐步把较重实现从公共头文件移入 `.cpp`，保留小型内联与模板实现。这样可以
减少依赖扩散、改善迭代编译时间，并把原生平台代码局限在实现层。保持 xmake
为主要入口，先把安装包/消费项目做好；是否额外支持 CMake 由实际用户需求决定。
